# 积存金价格采集与报表

每个工作日 **09:00–22:00 每个整点**抓一次金价（共 14 次），追加进 CSV，并生成一份可离线打开的单文件报表；
没采到的整点自动用**最近一次真实报价**补齐，让今日曲线始终连续；
另外每天从上金所日线取回当日**真实触及过的最高/最低价**。
**只读公开报价，不登录、不碰账户、不做任何交易。**

## 文件

| 文件 | 作用 |
|---|---|
| `collect.py` | 主程序：采集 → 写 CSV → 同步日内极值 → 生成报表 |
| `config.json` | 时点、目标价、**标定偏移**（估算中行价的关键参数） |
| `data/gold_price.csv` | 分时数据，一行一个时点，只追加。见下方「三种 src」 |
| `data/sge_extremes.json` | 上金所日线极值：按日期存当日开/收/最高/最低，最多保留 400 个交易日 |
| `report.html` | 报表，每次采集后自动重写，双击即看 |
| `data/run.log` | 定时任务运行日志（若用 launchd） |

## 采集时点（工作日 09:00–22:00，每个整点）

```
09:00 10:00 11:00 12:00 13:00 14:00 15:00
16:00 17:00 18:00 19:00 20:00 21:00 22:00
```

共 14 个时点。改 `config.json` 的 `slots` / `slot_names` 即可，代码按长度自适应。

**一次真实请求只落一行数据，落在「已经到的最后一个整点」上**——13:40 触发就记到 13:00，
不会顺手把 11:00、12:00 也填成同一个数（那是造假）。缺的整点另走补齐流程，见下节。

> 之所以覆盖到 22:00：实测源站在夜间**仍在刷新报价**。2026-10-30 白天尾盘 `854.50`，
> 当晚 22:43 已跌到 `840.50`，一天内差 14 元/克。只看白天会漏掉整段夜间的波动。

## 三种 `src`，报表里严格区分

| `src` | 含义 | 能不能当日线/收盘价 |
|---|---|---|
| `live` | 真实请求拿到的报价 | ✅ 唯一可当分时实采 |
| `carry` | 整点没采到，沿用最近一次实采价补齐 | ❌ 只用于让曲线连续 |
| `sge_daily` | 用上金所日线回溯出的历史价 | ✅ 历史日（无实采时） |

## 补齐机制（2026-10-30 改）：`fill_today()`

每次采集后自动跑一遍，把今天**缺失的整点**补成 `carry` 行：

- **只做前向沿用**：某整点用它**之前最后一次真实报价**，绝不拿后面才知道的价格回头填早先的时点（那是未来信息，会画出假走势）
- 早于当天第一条真实记录的整点（如整天没开机），退化为用当天第一条兜底
- 幂等：每次先清掉今天旧的 `carry` 行再重算，所以「先补了沿用值、后来整点采到真值」时，沿用值会让位
- 报表里 `carry` 行显示为**灰色**，标注「沿用 HH:MM 报价」，曲线上是**空心点**、不标数值

想让某个整点变成真值，唯一办法就是在那个整点跑一次采集。

## 手动跑一次

```bash
cd /Users/liubang/Money/黄金
/usr/bin/python3 collect.py             # 采集 + 出报表
/usr/bin/python3 collect.py --report    # 只重出报表，不采集
/usr/bin/python3 collect.py --force     # 忽略周末/时段限制
/usr/bin/python3 collect.py --backfill 30   # 用日线回填过去 30 个自然日（不含今天）
/usr/bin/python3 collect.py --auto          # 自动模式：该整点已有真实记录就静默跳过
/usr/bin/python3 collect.py --sync-extremes # 只同步上金所日内开/收/最高/最低，并重建报表
/usr/bin/python3 collect.py --fill-today    # 不采集，只用最近实采价补齐今天缺失的整点
/usr/bin/python3 collect.py --no-fill       # 采集但不自动补齐（调试用）
/usr/bin/python3 push_library.py            # 把报表覆盖推送到资料库（无新数据则跳过）
/usr/bin/python3 push_library.py --force    # 不管有没有新数据，强制推一次
```

## 自动同步到资料库

每次采集到新数据后，报表会**覆盖**推送到资料库里已有的页面「积存金」，
节点和链接保持不变，不会每天新增一条：

<https://www.workbuddy.cn/space/d/83kbBfHrVmGJxQT0VnIWfH>

- 覆盖靠 `library` skill 的 `page/import_html.py --node-block-id`，node 写在 `config.json` 的 `library.node_block_id`
- 幂等：以 CSV 最后一条有效记录的 `(ts, slot)` 为指纹，没新数据就不推，重复执行无副作用
- 推送结果记在 `data/push.log`，上次推送的指纹记在 `data/push_state.json`
- ⚠️ 指纹只看 CSV 数据有没有变。**改了报表逻辑但数据没变时不会自动推**，
  这时手动跑一次 `push_library.py --force`

⚠️ **推送离不开 WorkBuddy 客户端**。资料库接口靠会话级 `WORKBUDDY_CONFIG_DIR`
+ RPC token 鉴权，实测纯净环境（`env -i`）直接 `E_AUTH_FAILED`。
所以采集可以由 LaunchAgent 跑，推送只能由应用内定时任务触发 —— **客户端关着就不推**，
不会假装成功。

## 漏采怎么办：不留「缺采」，但也不伪造

某个整点没采到（机器休眠、接口失败、程序没开着），报表**不会留空行报警**，
而是由 `fill_today()` 用最近一次真实报价补成 `carry` 行（见上文「三种 src」）。
灰色 + 「沿用 HH:MM 报价」 + 曲线空心点，三重标注，不会被误读成实采。

### 四条实现约束（2026-10-30 修正）

1. **先判断，再联网**。先算出「该不该采」，无活可干就直接返回、不发请求。旧版顺序反了，
   于是「没活干」那次也白跑一次网络——一旦失败就写下 `slot=手动`、价格全空的假失败行。
2. **一次请求只落一行真实数据**。旧版会把所有缺口一次性填成同一个当前价，
   于是一天没开机再补一次，CSV 里就多出十几个数值完全相同的「分时点」。现已改掉。
3. **收盘后宽限**：`config.json` 的 `tail_grace`（默认 `22:30`）只用于补最后一个时点 `22:00`；
   开盘前（`< 09:00`）一律不采。
4. **失败行不冒名**：采集失败时 `slot` 记真实目标时点，不再写 `手动`。

回归测试：`python3 verify_schedule.py` —— 17 个用例，在 `/tmp` 副本里跑，
时间用 monkeypatch 固定、报价写死，全程不发网络请求，不碰真实 CSV。

## 历史数据：日线回溯（`--backfill`）

源站 `chnau99999.com` **不提供历史数据**（所有历史路径都 404，只有当前报价），
所以过去的价格改从**上海黄金交易所 Au99.99 日线**补齐：

- 接口：`POST https://www.sge.com.cn/graph/Dailyhq`，`instid=Au99.99`
- 返回：`[日期, 开, 收, 低, 高]`，2016-12-19 起，约 2390 条

回填规则（都是日线里真实存在的数，不插值、不编造）：

| 时点 | 取哪个值 |
|---|---|
| 09:00 开盘（slots[0]） | 当日**开盘价** |
| 其余所有时点 | 当日**收盘价** |

⚠️ 因此**同一天各时点是同一个数**（都是收盘价）——这不是「当天价格没动」，而是日线粒度只能给到这一步。
报表里这些行标 `src=sge_daily`、note 写「日线回溯」，图中日期带 `*`，数据质量栏也会点名。
「数值连续不变＝源站停更」的检测**只看 live 行**，不会被回填行误触发。

回填不含今天（今天留给定时任务实采），已存在的 `(日期, 时点)` 会跳过，可重复执行。

## 关于价格：这里是估算，不是官方报价

数据源 `chnau99999.com` 给的是**中国黄金**的公开报价（基础金价 / 销售价 / 回收价），
不是中国银行积存金的官方报价。中行那一路的价格由**标定偏移**换算而来：

```
估算中行买入价 = 源站基础金价 + offset_buy
估算中行卖出价 = 源站基础金价 + offset_sell
```

当前标定（2026-10-30 10:54，实测）：

| 项 | 数值 |
|---|---|
| 源站基础金价 | 857.70 |
| 你在中行 App 看到：买入 / 卖出 | 874.33 / 856.73 |
| offset_buy | **+16.63** |
| offset_sell | **−0.97** |

实测复核：同一算法在 857.60 时算出 874.23，与你 App 的 874.33 相差 0.10 元/克。

**什么时候要重新标定**：中行调整加点、黄金基准价大幅变动后点差走形、
或报表里的估算价与 App 连续多次差 1 元以上。改 `config.json` 的
`calibration.offset_buy / offset_sell` 两个数即可，其余不用动。

## 日线展示口径：当天最后一个采集点即收盘价

2026-10-30 起，日线口径从「只认 14:50 尾盘」改为**取当天最后一个真实采集点**（用户要求）。

| 哪一天 | 取哪个价 |
|---|---|
| **任一交易日** | 当天**最后一条真实记录**（`live` 或 `sge_daily`，`carry` 不算） |
| **当天** | 同上。未采到 `22:00` 前标 `~`（尚未定盘），采到后即为当日收盘价 |

改这条口径的原因：原来要求必须采到尾盘时点，否则那一天**整段从日线图上消失**——
没有比"平白缺一天"更糟的展示。现在只要当天有过任意一次采集就有一条日线。

- **排除 `carry`**：那是沿用前值的估算，拿它当收盘价等于凭空造数据。
- 采到 `22:00` 视为**定盘**，图上不再标 `~`。
- 日环比以上一交易日**最后一条真实记录**为基准；若那天最后一条不是收尾时点，
  指标卡写「上日末点」而不是「上日收盘」，口径不混。
- 回填的历史日线存的就是当日收盘价，与这个口径天然一致。

## 日内极值：上金所日线里的真实最高/最低

报表新增「日内极值」折线图和「今日日内最低」卡片，数据来自上金所 Au99.99 日线，
是当天**真实触及过**的最低/最高价，已用同一个 `offset_buy` 换算成估算中行买入价。

### 报表里的两块折线图（多维度，一维度一线一色）

| 区块 | 三条线 | 配色 |
|---|---|---|
| 日内极值 · 近 15 个交易日 | 日内最低 / 日内最高 / 日线收盘 | 绿 `#2f9e68` / 红 `#e5484d` / 金 `#e0b354`（涨红跌绿） |
| 今日明细 · 09:00~22:00 逐小时 | 估算买入 / 估算卖出 / 基准金价 | 金 `#e0b354` / 蓝 `#58a6ff` / 灰 `#8b949e` |

实现要点（`svg_multiline()`，与单线的 `svg_chart()` 并存）：

- 多线共用一条纵轴，取值域覆盖**所有**维度，不做各自归一化——否则三条线的相对高低就是假的
- 日内极值额外铺了一条**最低~最高的半透明色带**，带子越宽＝当天波动越大
- 每个点带 `<title>`，鼠标悬停显示「维度 横轴：数值」；精确到分的数值表折叠在 `<details>` 里
- 沿用值仍画空心环，与实采的实心点区分，且提示里标注「沿用值」
- 估算卖出与基准金价只差 `offset_sell`（-0.97），两条线几乎重合是真实点差，不是画错

**为什么单列这一块**：先前研究过，就算加密到每小时采 6 次，也只是 6 个离散瞬间，
盘中一闪而过的低点照样躲得过去——2026-10-30 实测，3 次采样里的最低是 `854.50`，
而当天真实最低是 `853.50`，整整漏掉 1.00 元/克；当日最高 `867.00` 更是完全没看到。
交易所汇总的 low/high 不同，只要当天到过某个价就一定留痕，比自己加密采样可靠得多。

- 数据来源同 `--backfill`：`POST https://www.sge.com.cn/graph/Dailyhq`，`instid=Au99.99`
- 返回 `[日期, 开盘, 收盘, 最低, 最高]`。**字段顺序已用 4! 全排列穷举校验**：
  该假设 2392 条里只有 17 条不满足 `low ≤ min(开,收)`（且都是源站自身几分钱的舍入误差），
  次优假设要违规 1778 条 → 结论可靠
- 每次采集成功后自动调用，**失败只记日志、绝不影响采集主流程**；也可手动 `--sync-extremes`
- 落在 `data/sge_extremes.json`，按 `config.json` 的 `sge.keep_days` 保留最近 N 个交易日
- 换算沿用 `offset_buy`，与分时估算价同源可比
- ⚠️ **当日极值由上金所在收盘后提供**，盘中看到的可能只是截至当时的部分区间

## 定时任务：一个 LaunchAgent 管 14 个整点

`~/Library/LaunchAgents/com.liubang.goldprice.plist` 里是一个任务、14 个 `StartCalendarInterval` 条目：

```
09:00 / 10:00 / 11:00 / 12:00 / 13:00 / 14:00 / 15:00
16:00 / 17:00 / 18:00 / 19:00 / 20:00 / 21:00 / 22:00      周一至周五
```

周末不过滤，由脚本内的 `weekdays_only` 自行跳过。

启用（任选其一）：

```bash
# 立刻生效
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.liubang.goldprice.plist
```

或者**什么都不做**：macOS 在下次登录（重启）时会自动加载 `~/Library/LaunchAgents/` 下的任务。

> ⚠️ **在 LaunchAgent 生效之前，很多整点都是「沿用」值**。
> 应用内那条 hourly 定时任务的**实际触发时间会漂移**——2026-10-30 实测触发在 `13:32`、`14:49`，
> 都不是整点。好处是漂移变得不痛：13:40 触发就记到 13:00，不会丢数据；
> 代价是没被准点采到的整点只能沿用前一个真实报价（灰色 `carry` 行）。
> 想拿到准点的整点快照，只能让上面的 LaunchAgent 真正加载起来。

检查是否生效：

```bash
launchctl list | grep goldprice
tail -n 20 /Users/liubang/Money/黄金/data/run.log
```

停用：

```bash
launchctl bootout gui/$(id -u)/com.liubang.goldprice
```

> 应用内那条定时是 `FREQ=HOURLY;INTERVAL=1;BYDAY=MO~FR;BYHOUR=9..22`，每小时触发一次。
> 早先以为应用任务写不了多时点——其实是规则：`FREQ=WEEKLY` 下 `BYHOUR` 只能填**单个整点**，
> 而 `FREQ=HOURLY` 支持多值。所以现在两条链路是互补关系：
> **launchd 负责准点，应用内任务负责兜底并把报表推送到资料库**（推送依赖客户端，launchd 做不到）。

## 已知限制（都写进报表的「数据质量」栏，不藏）

1. **源站不公布更新时间戳**，页面里没有时间字段。程序用「数值连续 N 次不变」来提示可能停更。
2. 中行价是估算值，实际成交以 App 为准；买卖价差 17 元左右，来回一趟成本不低。
3. 节假日不判断：中国法定假日休市时脚本照样跑，会记下不变的价格，报表会提示。
4. 机器休眠会漏采。**漏掉的整点不会显示为「缺采」**——`fill_today()` 会用最近一次真实报价补成
   `carry` 行，note 记「沿用 HH:MM 报价」，报表里灰色显示。这些值**不是该整点的真实价格**，
   只用于让曲线连续；日线与收盘价也不用它们。想变成真值，只能在对应整点跑一次采集。
5. 报表只给数字和相对位置，**不给买卖建议**。
6. 回填数据来自**上金所 Au99.99 基准日线**，不是中行分时报价；换算成「中行价」仍靠同一个标定偏移，
   而一个月前的银行点差未必等于今天，**回溯出的中行价误差可能比实时估算更大**。看趋势可以，别拿它当历史成交凭证。
